# 上下文退化模式

语言模型随上下文增长表现出可预测的退化模式。理解这些模式对于诊断故障和设计弹性系统至关重要。

## 激活场景

- Agent在长对话中性能意外下降
- 调试Agent产生错误或不相关输出
- 设计必须可靠处理大上下文的系统
- 调查"lost in middle"现象

## 退化模式

### 1. Lost-in-Middle（中间丢失）

**现象**：U型注意力曲线，中间信息召回率降低10-40%

**原因**：
- 第一个token（BOS）吸收大量注意力（注意力沉淀）
- 随上下文增长，预算被稀释
- 训练数据以短序列为主

**缓解**：
- 关键信息放开头或结尾
- 使用摘要结构在有利位置浮现关键信息
- 用明确的分节标题帮助模型导航

### 2. Context Poisoning（上下文中毒）

**现象**：幻觉/错误进入上下文并通过反复引用复合

**进入路径**：
- 工具输出包含错误
- 检索文档包含过时信息
- 模型生成的摘要引入幻觉

**症状**：
- 之前成功的任务输出质量下降
- 工具错位（调用错误工具或参数）
- 幻觉在纠正尝试后持续

**恢复**：截断到中毒前的上下文，或用干净上下文重启

### 3. Context Distraction（上下文分心）

**现象**：模型过度关注提供的信息，忽视训练知识

**原因**：
- 模型必须关注所有提供的内容
- 无关信息与相关信息竞争有限的注意力预算
- 即使单个无关文档也会降低性能

**缓解**：
- 加载检索文档前应用相关性过滤
- 使用命名空间和组织使无关部分易于忽略
- 考虑信息是否真的需要在上下文中

### 4. Context Confusion（上下文混淆）

**现象**：无关信息以降低质量的方式影响响应

**表现**：
- 响应针对查询的错误方面
- 工具调用似乎适合不同任务
- 输出混合来自多个来源的要求

**解决方案**：
- 明确的任务分割
- 不同任务使用不同上下文窗口
- 任务上下文之间清晰过渡

### 5. Context Clash（上下文冲突）

**现象**：累积信息直接冲突，产生矛盾指导

**来源**：
- 多源检索有矛盾信息
- 过时和当前信息同时出现
- 不同视角有效但不兼容

**解决方案**：
- 明确标记冲突并请求澄清
- 建立优先级规则（哪个来源优先）
- 版本过滤排除过时信息

## 退化阈值参考

| 模型 | 退化开始 | 严重退化 |
|------|----------|----------|
| GPT-5.2 | ~64K tokens | ~200K tokens |
| Claude Opus 4.5 | ~100K tokens | ~180K tokens |
| Claude Sonnet 4.5 | ~80K tokens | ~150K tokens |
| Gemini 3 Pro | ~500K tokens | ~800K tokens |

## 四桶策略

| 策略 | 说明 |
|------|------|
| **Write** | 保存上下文到窗口外（便签、文件系统） |
| **Select** | 通过检索、过滤将相关上下文拉入窗口 |
| **Compress** | 通过摘要、抽象减少token同时保留信息 |
| **Isolate** | 跨子代理分割上下文防止单一上下文过大 |

## 关键原则

1. 监控开发期间上下文长度与性能的相关性
2. 在退化变严重前实施压缩触发器
3. 添加到上下文前验证检索文档的准确性
4. 使用版本控制防止过时信息导致冲突
5. 分割任务防止不同目标间的上下文混淆
6. 为优雅退化设计，而非假设完美条件
